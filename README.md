# کلاس‌میت — سیستم برگزاری کلاس آنلاین

سیستم ویدئوکنفرانس سبک و کم‌مصرف مشابه گوگل میت، بهینه برای اجرا روی سرورهای ضعیف (۱ هسته CPU و ۲ گیگابایت رم) با ظاهر گلس‌مورف در پالت فیروزه‌ای و رابط فارسی راست‌به‌چپ، تا **۱۸ نفر** همزمان.

## معماری و بهینه‌سازی برای منابع کم

نکته کلیدی معماری: **هیچ رسانه‌ای از سرور عبور نمی‌کند**. ویدئو و صدا مستقیماً بین شرکت‌کننده‌ها (WebRTC Mesh) ردوبدل می‌شود و سرور فقط نقش «سیگنالینگ» را دارد (ردوبدل SDP/ICE از طریق Socket.IO). در نتیجه بار CPU و پهنای‌باند سرور ناچیز است و سیستم روی سخت‌افزار ضعیف به‌راحگی اجرا می‌شود.

| بخش | تکنولوژی | منبع مصرفی |
|---|---|---|
| وب‌اپ (Next.js 16 + TypeScript + Tailwind 4 + shadcn/ui) | رندر صفحات | فقط HTML/JS استاتیک |
| سیگنالینگ (Socket.IO روی Bun) | ردوبدل offer/answer/ICE | چند صدا فراخوان، MB کمی رم |
| رسانه (WebRTC Mesh) | ویدئو/صدا P2P | هیچ — ترافیک بین کاربران |

تصویر ویدئویی با کیفیت ۶۴۰×۳۶۰ در ۱۵ فریم و حداکثر ~۲۶۰ کیلوبیت‌برثانیه ارسال می‌شود تا اتصال‌های ضعیف هم پایدار بمانند؛ اشتراک صفحه تا ~۵۰۰ کیلوبیت‌برثانیه.

## امکانات

- ساخت جلسه با کد یکتا (مثل `abc-defg-hij`) و ورود با کد یا لینک اشتراکی (`/#/room/<code>`)
- پیش‌نمایش دوربین قبل از ورود با کلیدهای میکروفون/دوربین (مثل صفحه آماده‌به‌کار گوگل میت)
- ویدئو و صدای P2P با حالت‌های گرید، اسپات‌لایت و پین‌کردن
- اشتراک صفحه (جایگزینی Track بدون نegotiation مجدد، با اسپات‌لایت خودکار)
- چت زنده با شمارنده پیام خوانده‌نشده
- پنل شرکت‌کننده‌ها با وضعیت میکروفون/دوربین/دست
- بالا بردن دست و واکنش‌های شناور
- کنترل‌های میزبان: قطع صدای همه، اخراج فرد، و **انتقال خودکار میزبانی** در صورت خروج میزبان
- تشخیص گوینده فعال (حلقه صوتی روی کاشی)
- تایمر جلسه، نمایشگر وضعیت اتصال، اعلان‌های ورود/خروج
- حالت «تماشا»: اگر دوربین/میکروفون در دسترس نباشد کاربر بدون رسانه هم وارد می‌شود
- قطع شدن لحظه‌ای اینترنت به‌صورت خودکار ترمیم می‌شود (rejoin خودکار + ICE restart)

## اجرای محلی (توسعه)

```bash
bun install

# ترمینال ۱ — سرور سیگنالینگ (پورت 3003)
cd mini-services/signaling && bun run dev

# ترمینال ۲ — وب‌اپ (پورت 3000)
bun run dev
```

سپس `http://localhost:3000` را باز کنید. کلاینت به‌صورت پیش‌فرض از مسیر نسبی `/?XTransformPort=3003` به سیگنالینگ وصل می‌شود (سازگار با گیت‌وی این پروژه).

## دیپلوی روی سرور با Docker Compose

```bash
docker compose up -d --build
# یا با پورت دلخواه:
CLASSMEET_PORT=8080 docker compose up -d
```

سه سرویس راه‌اندازی می‌شود: `app` (Next.js)، `signaling` (Socket.IO) و `caddy` به‌عنوان نقطه ورود واحد:

- `/socket.io/*` → سیگنالینگ:3003
- بقیه مسیرها → اپ:3000

سپس `http://SERVER_IP` را در مرورگر باز کنید.

### متغیرهای محیطی

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `NEXT_PUBLIC_SIGNALING_URL` | `/?XTransformPort=3003` | آدرس سوکت؛ در دیپلوی داکر خالی (same-origin) |
| `NEXT_PUBLIC_SOCKET_PATH` | `/` | مسیر Socket.IO؛ در دیپلوی داکر `/socket.io` |
| `CLASSMEET_PORT` | `80` | پورت عمومی Caddy |

## گیت‌هاب اکشنز

فایل `.github/workflows/ci.yml` شامل دو job است:

1. **quality** — روی هر push/PR: نصب با Bun، اجرای ESLint، بیلد کامل Next.js و بیلد تستی سرور سیگنالینگ
2. **docker** — روی push به `main`: انتشار دو ایمیج به GitHub Container Registry:
   - `ghcr.io/<user>/classmeet-app:latest`
   - `ghcr.io/<user>/classmeet-signaling:latest`

اجرا با ایمیج‌های آماده GHCR روی سرور:

```bash
docker pull ghcr.io/<user>/classmeet-app:latest
docker pull ghcr.io/<user>/classmeet-signaling:latest
```

## نکته TURN (شبکه‌های سخت)

WebRTC در اکثر شبکه‌ها با STUN عمومی گوگل کار می‌کند؛ فقط کاربرانی که پشت NAT متقارن (معمولاً اینترنت سیم‌کارت) هستند ممکن است متصل نشوند. برای پوشش کامل، یک `coturn` سبک روی همان سرور اجرا کنید و آدرسش را به `RTC_CONFIG` در `src/lib/meeting.ts` اضافه کنید (نمونه در `docker-compose.yml` کامنت شده است).

src/components/meeting/           # کاشی ویدئو، نوار کنترل، پنل چت/شرکت‌کننده‌ها
